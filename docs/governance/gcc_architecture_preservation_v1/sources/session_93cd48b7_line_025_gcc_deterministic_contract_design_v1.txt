## Gemeinsame Regeln

Alle Objekte sind kanonisch serialisiert, versionsfest und nach dem ersten Commit unveränderlich. Neue Erkenntnis erzeugt ein neues Objekt mit neuer Version und Verweis auf das vorige. Unbekannte Werte stehen als `UNKNOWN`. Auslassen bedeutet nicht „falsch“ oder „unbetroffen“.

`CASE_ID` ist `gcc-case-v1:` plus SHA-256 der kanonischen `GCC_REQUEST_V1` ohne `case_id`. Dieselbe Anfrage ergibt dieselbe ID. GCC vergibt keine zweite ID für denselben Inhalt.

Es gibt keine KI-Funktion, keinen Hauptwächter-zu-Hauptwächter-Kanal und keine Trading-, Code-, Safety-Override- oder Owner-Approval-Autorität. Die 20 vorbereiteten Domänen und 60 Einzelverträge bleiben `NOT_RATIFIED` und sind keine Empfänger. WITHHELD bleibt eine Coverage-Lücke.

| `affected_contract_ids` | list | Leer ist zulässig und bedeutet „keine vorab benannt“, nicht „keine Wirkung“ |
| `current_commit` | `97c8c954…` für diesen Pin | Ein Commit |
| `current_tree` | `898ede79…` für diesen Pin | Ein Tree |

| Feld | Typ | Invariante |
| --- | --- | --- |
| `schema` | const `GCC_DISPATCH_V1` | Pflicht |

| `registry_version` | string | Dieselbe Version für den ganzen Fall |
| `registry_digest` | hex | Digest der ratifizierten Empfängermenge |
| `dispatch_kind` | `INITIAL` \| `CAUSAL_FOLLOWUP` | Initial an alle ratifizierten Guardians; Follow-up nur mit belegter Kante |
| `causal_evidence_ref` | ref \| null | Bei `INITIAL` null. Bei Follow-up eine vorhandene Kanten- oder Contract-ID |
| `recipient_guardian_id` | string | `ratification_status=RATIFIED` |
| `dispatch_id` | string | Eindeutig je `(case_id, request_version, recipient, dispatch_kind, causal_evidence_ref)` |

| `dedup_key` | string | Gleicher Schlüssel wird nicht erneut fachlich zugestellt |

**Invarianten.** Das Register ist endlich und versioniert. `NOT_RATIFIED`, `WITHHELD` und unbekannte Bereiche erscheinen nur unter `coverage_gaps`, nie als Empfänger. Eine neu belegte Forward-, Reverse-, transitive oder zyklische Kante erzeugt höchstens eine deduplizierte Folgeanfrage an den zuständigen ratifizierten Guardian. GCC erfindet keine Kante. Ein leeres ratifiziertes Register ist ein gültiger Initialversand und zugleich eine offene Lücke.

## 3. GCC_GUARDIAN_RESPONSE_V1

| Feld | Typ | Invariante |
| --- | --- | --- |
| `schema` | const `GCC_GUARDIAN_RESPONSE_V1` | Pflicht |
| `case_id`, `request_version`, `dispatch_id` | ref | Muss zum Dispatch passen |
| `guardian_id` | string | Nur der adressierte Guardian |
| `response_version` | int | Monoton; alte Version bleibt lesbar |
| `impact_status` | `BETROFFEN` \| `NICHT_BETROFFEN` \| `UNGEKLÄRT` | Genau einer |
| `claim_id` | string | Eigene Claim-ID |
| `scope_ref` | ref | Exakt der Request-Scope oder eine ausgewiesene Teilmenge |
| `direction` | `FORWARD` \| `REVERSE` \| `TRANSITIVE` \| `NONE_IN_SCOPE` \| `UNKNOWN` | Bei `BETROFFEN` nicht `UNKNOWN` |
| `reach` | `EXISTS` \| `WIRED` \| `REACHABLE` \| `ACTIVE` \| `UNKNOWN` | Stufen bleiben getrennt |
| `contract_or_edge_ids` | list | Bei `BETROFFEN` nicht leer |
| `tool_slots` | genau drei | `<DOMAIN> GHV`, `<DOMAIN> Graph`, `<DOMAIN> GHOSV` |
| `dimensions` | genau fünf | Kapitel 21.1 |
| `evidence_refs` | list | CURRENT-Commit, Tree, Pfad oder Contract |
| `counterevidence_refs` | list | Darf leer sein, muss dann `NONE_FOUND_IN_SCOPE` sagen |
| `uncertainty` | list | Bei `UNGEKLÄRT` nicht leer |
| `negative_proof` | object \| null | Pflicht und nicht null bei `NICHT_BETROFFEN` |
| `foreign_interpretation` | const `false` | |

Jedes Tool-Slot trägt `position_name`, `execution_status` (`EXECUTED`, `NOT_EXECUTED`, `TOOL_UNAVAILABLE`, `NOT_APPLICABLE`), `evidence_ref`, `depth_status` und die getrennten Marker `NAMED`, `EXISTS`, `IMPLEMENTED`, `APPLICABLE`, `VERIFIED`, `ACTIVE`, `OWNER_AUTHORIZED`. `NOT_APPLICABLE` braucht eine Scope-Begründung. GHOSV Execution bleibt execution-only. Ein nicht ausgeführtes Pflichtwerkzeug ist kein Negativnachweis.

Die fünf Dimensionen sind `STRUKTUR_KAUSALITAET`, `VERTRAEGE_AUTORITAET`, `DATEN_ZUSTAND`, `RUNTIME_SCHUTZ`, `AUSSENGRENZEN`. Jede hat `coverage_status` und `uncertainty_status`.

**Statusregeln.**

- `BETROFFEN`: eigene Contract- oder Kanten-ID, CURRENT-Beleg, Richtung und Reichweite.
- `NICHT_BETROFFEN`: endlicher Scope, Prüfung der eigenen Schnittstellen, dokumentierte Abwesenheit der relevanten Wirkung, alle drei Tool-Slots berichtet, keine Dimension `UNGEKLÄRT`.
- `UNGEKLÄRT`: fehlende Antwort, fehlende Daten, Toolausfall, unklare Semantik, unbewiesene Erreichbarkeit, offene Kante, veralteter Graph oder unbenannte Kantenmenge.
- Eine Dimension `UNGEKLÄRT` oder ein Tool `NOT_EXECUTED` / `TOOL_UNAVAILABLE` erzwingt den Impact-Status `UNGEKLÄRT`.

## 6. GCC_CASE_LIFECYCLE_V1

Normativ ist die Übergangstabelle. `CLOSED` ist Endzustand und bedeutet allein, dass der Fall nicht mehr fortschreitet.

| Von | Nach | Bedingung |
| --- | --- | --- |
| `INTAKE` | `PINNED` | Schema gültig, Text-Hash gleich, `change_authorization=ABSENT` |
| `PINNED` | `DISPATCHED` | Ein Commit, ein Tree, eine Registry-Version |
| `DISPATCHED` | `COLLECTING` | Für jeden ratifizierten Empfänger ein Initial-Dispatch, Ack noch offen erlaubt |
| `COLLECTING` | `VALIDATING` | Kein offener Erst- oder Folge-Dispatch innerhalb der Attempt-Grenze |
| `VALIDATING` | `COLLECTING` | Neue belegte Kante ohne Folge-Dispatch |
| `VALIDATING` | `IMPACT_OPEN` | Lücke, Timeout, Widerspruch, Toollücke, ungebundener Parameter oder leeres Register |
| `VALIDATING` | `IMPACT_BOUNDED` | Validation `PASS` und Report `BOUNDED_VERIFIED` |
| `IMPACT_OPEN` | `OWNER_REVIEW` | Report persistiert und als offen gekennzeichnet |
| `IMPACT_BOUNDED` | `OWNER_REVIEW` | Report persistiert |
| `OWNER_REVIEW` | `CLOSED` | Owner-Entscheid als externes Objekt gespeichert |
| `INTAKE`…`OWNER_REVIEW` | `CLOSED` | Abbruchgrund gesetzt |

Abbruchgründe: `REQUEST_MUTATED`, `BASELINE_MISMATCH`, `STALE_BASELINE`, `UNAUTHORIZED_WRITE_OR_POST`, `FOREIGN_INTERPRETATION`, `ATTEMPT_LIMIT_WITH_GAP`, `AUTHORITY_ESCALATION_ATTEMPT`, `OWNER_STOP`. Ein Abbruch löscht keine bereits gespeicherten Befunde.

`IMPACT_OPEN` geht nicht nach `IMPACT_BOUNDED`, ohne erneut `VALIDATING` zu durchlaufen. `IMPACT_BOUNDED` geht nicht nach `CLOSED` unter Umgehung von `OWNER_REVIEW`.

**Reproof.** Eine genehmigte Änderung ist ein anderes Owner-Objekt und kein GCC-Übergang. Danach entsteht ein neuer Fall mit neuem Pin, `reproof_of=alte case_id`. Alte Befunde werden referenziert und nicht als Befunde des neuen Trees übernommen. `IMPACT_BOUNDED` des alten Falls gilt nach dem ersten abweichenden Commit oder Tree nicht weiter. Category-3-Flächen bleiben auch im Reproof gesperrt, bis ein separates Owner-GO genau diese Änderung nennt.

```mermaid
stateDiagram-v2
  [*] --> INTAKE
  INTAKE --> PINNED
  PINNED --> DISPATCHED
  DISPATCHED --> COLLECTING
  COLLECTING --> VALIDATING
  VALIDATING --> COLLECTING
  VALIDATING --> IMPACT_OPEN
  VALIDATING --> IMPACT_BOUNDED
  IMPACT_OPEN --> OWNER_REVIEW
  IMPACT_BOUNDED --> OWNER_REVIEW
  OWNER_REVIEW --> CLOSED
  INTAKE --> CLOSED
  PINNED --> CLOSED
  DISPATCHED --> CLOSED
  COLLECTING --> CLOSED
  VALIDATING --> CLOSED
  IMPACT_OPEN --> CLOSED
  IMPACT_BOUNDED --> CLOSED
  OWNER_REVIEW --> CLOSED
```
