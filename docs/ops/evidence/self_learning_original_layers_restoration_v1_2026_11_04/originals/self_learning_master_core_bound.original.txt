# Peak_Trade Self-Learning System – Master Implementation Runbook

**Status:** Architektur-/Implementierungs-Runbook  
**Zweck:** Aufbau eines geschlossenen, reproduzierbaren, Safety-First Self-Learning Systems für Peak_Trade  
**Grundprinzip:** `SELF_LEARNING != SELF_AUTHORIZING`

---

## 1. Executive Objective

Peak_Trade soll von einem fragmentierten Experiment-/Feedback-Framework zu einem **geschlossenen Learning System** weiterentwickelt werden, das aus Research-, Shadow-, Testnet- und später bounded Live-Evidence systematisch lernt, ohne jemals selbstständig Trading Authority zu erhalten.

Das System soll autonom:

- beobachten,
- Experimente ausführen,
- Ergebnisse reproduzierbar bewerten,
- Robustness prüfen,
- Fehler und widerlegte Hypothesen erinnern,
- Champion und Challenger vergleichen,
- Reality Gaps zwischen Backtest und beobachteter Realität erkennen,
- Cost-/Execution-Model-Kandidaten erzeugen,
- Research-Hypothesen priorisieren,
- Offline-Research automatisieren,
- seinen eigenen Research-Prozess später meta-analysieren.

Das System darf niemals autonom:

- `LIVE_AUTHORIZED=true` setzen,
- `enabled` oder `armed` setzen,
- Confirm-Tokens erzeugen oder verwenden,
- Canary autorisieren,
- Orders senden,
- Funding ausführen,
- Risk Limits erhöhen,
- Leverage erhöhen,
- produktive Runtime-Config mutieren,
- einen Challenger eigenständig zum Live-Champion promoten.

### Kerninvariante

```text
SELF_LEARNING != SELF_AUTHORIZING
```

Die Learning Plane erzeugt ausschließlich **Evidence, Candidates, Comparisons, Research Priorities und Proposals**.

Die Authority / Execution Plane bleibt separat und wird weiterhin ausschließlich durch bestehende Governance, Safety Gates und explizite Owner-Autorisierung kontrolliert.

# 2. Forensischer Ist-Zustand

Die bisherige forensische Bestandsaufnahme klassifiziert Peak_Trade als:

```text
CURRENT_LEARNING_SYSTEM_CLASSIFICATION=
EXPERIMENT_FRAMEWORK_WITH_FEEDBACK_COMPONENTS
```

Heute existieren drei teilweise getrennte Welten:

## 2.1 Productive Runtime Plane

Produktive bzw. kanonische Laufzeit:

```text
Market Data
→ Features / Regime
→ Strategy / Master Decision
→ Risk
→ Safety
→ Intent
→ Simulated Execution
→ Evidence
→ Verification
```

Dieser Graph besitzt heute **keinen geschlossenen Learning Loop**.

## 2.2 Neue Learning-Plane Contracts

Neuere Komponenten unter anderem in:

```text
src/meta/learning_loop/*
```

arbeiten fail-closed und offline.

Sie können vorhandene Evidence:

- projizieren,
- vergleichen,
- klassifizieren,
- als Learning Input darstellen,
- als Candidate-/Comparison-Evidence strukturieren.

Sie trainieren oder promoten jedoch bewusst nicht autonom.

Das ist aus Safety-Sicht die richtige Richtung.

## 2.3 Legacy Learning / Promotion Plane

Ältere Pfade umfassen unter anderem:

```text
src/meta/learning_loop/bridge.py
src/meta/learning_loop/emitter.py
scripts/run_learning_apply_cycle.py
scripts/run_promotion_proposal_cycle.py
src/governance/promotion_loop/*
src/core/peak_config.py
config/auto/*
config/live_overrides/*
```

Diese Komponenten besitzen fachlich potenziell wertvolle Mechanismen, enthalten aber auch eine **latente Config-Mutationsarchitektur**.

Besonders kritisch zu adjudizieren:

```text
Learning / Promotion Proposal
→ bounded_auto
→ config/live_overrides/auto.toml
→ load_config_with_live_overrides()
```

Nach bisherigem Befund ist dieser Pfad aktuell **nicht produktiv an den Host verdrahtet**.

Das reduziert das akute Risiko, beseitigt aber nicht das Architekturproblem.

Die Legacy-Komponenten dürfen deshalb weder blind übernommen noch blind entfernt werden.

# 4. Architectural Invariants

Die folgenden Invarianten gelten während des gesamten Programms.

```text
SELF_LEARNING_SELF_AUTHORIZING_SEPARATION=true

LEARNING_CAN_WRITE_LIVE_CONFIG=false
LEARNING_CAN_INCREASE_RISK=false
LEARNING_CAN_INCREASE_LEVERAGE=false
LEARNING_CAN_FUND=false
LEARNING_CAN_SUBMIT_ORDER=false
LEARNING_CAN_ARM=false
LEARNING_CAN_ENABLE=false
LEARNING_CAN_CREATE_CONFIRM_TOKEN=false
LEARNING_CAN_USE_CONFIRM_TOKEN=false
LEARNING_CAN_AUTHORIZE_CANARY=false
LEARNING_CAN_PROMOTE_TO_LIVE=false
```

Zusätzlich:

- Historical Evidence ist immutable.
- Experimente dürfen keine historischen Registry-Einträge überschreiben.
- Kein stiller Default auf `0` für Fees, Slippage oder Funding.
- Keine produktive Promotion allein auf Basis von Sharpe.
- Keine impliziten Experiment-Inputs.
- Keine automatische Risk-Erhöhung als Resultat einer Optimierung.
- Keine direkte Verbindung `model output → order submit`.
- Kein Research-System darf Live-/Testnet-Config als normalen Output behandeln.
- Das Self-Learning-System muss an den kanonischen Peak_Trade Trading Decision Core gebunden sein und darf keine konkurrierende, semantisch unabhängige Bull/Bear-/Regime-/Decision-Logik als stillen Ersatz etablieren.
- Änderungen an Bull/Bear-, State-Switch-, Survival-, Suitability-, Double-Play-, Entry-/Exit- oder anderen kanonischen Trading-Decision-Komponenten müssen über Experiment Identity, Evidence und Lineage eindeutig versioniert und vergleichbar sein.
- Learning darf Core-Logic-Verbesserungen erforschen, bewerten und als Candidate/Proposal ausgeben, aber produktive Handelslogik niemals autonom ersetzen oder mutieren.

## 4.1 Canonical Trading Core Learning Binding

Zusätzlich zur Authority-Separation gilt als harte Architektur-Invariante:

```text
SELF_LEARNING_MUST_LEARN_FROM_CANONICAL_TRADING_DECISION_PATH=true
LEARNING_MAY_RESEARCH_CORE_LOGIC_CHANGES=true
LEARNING_MAY_AUTONOMOUSLY_REPLACE_CORE_LOGIC=false
```

Der primäre fachliche Lernpfad muss die tatsächlich verwendete kanonische Peak_Trade-Entscheidungskette beobachtbar machen:

```text
Canonical Market Context
→ Scope
→ Bull/Bear
→ State Switch
→ Survival
→ Suitability
→ Double Play
→ Entry / Position / Exit Decision
→ Risk / Sizing Context
→ Execution Outcome
→ Economic Outcome
→ Learning Evidence
```

Das Learning System soll dadurch nicht nur aggregierte Performance-Metriken optimieren, sondern kausal bzw. attributionell untersuchen können, **welcher Teil der kanonischen Handelslogik** zu einem guten oder schlechten Ergebnis beigetragen hat.

Mindestens folgende Fragestellungen müssen später über versionierte Evidence analysierbar sein:

- War die Bull-/Bear-Klassifikation korrekt, falsch, zu früh oder zu spät?
- War ein Bull→Bear- oder Bear→Bull-State-Switch fachlich und zeitlich angemessen?
- Welche Candidate-/Confirmed-Übergänge funktionieren stabil und welche erzeugen False Positives?
- In welchen Markt- und Regimebedingungen versagen Survival oder Suitability?
- Welche Double-Play-Konstellationen liefern robuste bzw. instabile Ergebnisse?
- War die Richtungs-/Signalentscheidung korrekt, aber Entry, Position Management oder Exit ökonomisch schlecht?
- War die Trading Decision korrekt, verlor ihren Edge aber durch Fees, Slippage, Funding, Spread, Latency oder Liquidity?
- Welche Core-Logic-Parameterregionen sind OOS-, Walk-Forward-, Stress- und regimeübergreifend stabil?
- Welche Teile der Decision Chain erklären Drawdown, Tail Risk, Turnover oder PnL tatsächlich?
- Welche vorgeschlagenen Änderungen verbessern robuste Economic Outcomes, ohne Risk, Leverage oder Authority als Optimierungsabkürzung zu verwenden?

Wichtig:

```text
LEARNING_OUTPUT != CORE_LOGIC_MUTATION
```

Erkannte Verbesserungen an der kanonischen Handelslogik werden ausschließlich als versionierte Research-Hypothesen, Candidates, Comparisons und Promotion Evidence behandelt. Jede spätere produktive Änderung der Handelslogik bleibt ein separat governter Software-/Owner-Entscheid.

# 6. Phase 1 – Canonical Experiment Identity

## Ziel

Jedes Experiment erhält eine vollständige, deterministische und immutable Identität.

Ein Ergebnis ist nur dann vertrauenswürdig, wenn exakt rekonstruierbar ist:

- welcher Code,
- welche Strategie,
- welche Parameter,
- welche Daten,
- welches Feature Set,
- welche Kostenmodelle,
- welche Risk Policy,
- welche Portfolio-Zusammensetzung,
- welche Splits,
- welcher Seed,
- welche Runtime-/Environment-Version

verwendet wurden.

## Canonical Experiment Identity

Mindestens:

```text
experiment_identity
├── git_sha
├── strategy_identity
├── strategy_params_digest
├── trading_decision_core_digest
│   ├── market_context_contract_digest
│   ├── bull_bear_logic_digest
│   ├── state_switch_logic_digest
│   ├── survival_logic_digest
│   ├── suitability_logic_digest
│   ├── double_play_logic_digest
│   └── entry_position_exit_logic_digest
├── dataset_digest
├── feature_pipeline_digest
├── cost_model_digest
│   ├── fee_model_digest
│   ├── slippage_model_digest
│   └── funding_model_digest
├── risk_policy_digest
├── portfolio_digest
├── split_policy_digest
├── seed
├── environment_digest
└── parent_lineage_ref
```

## Keine impliziten Inputs

Folgende Inputs dürfen nicht mehr außerhalb der Identity leben:

- Fee assumptions
- Slippage assumptions
- Funding assumptions
- Seeds
- Dataset version
- Split policy
- Risk policy
- Portfolio definition
- critical feature settings
- canonical trading-decision-core version / digest
- Bull/Bear logic version
- State-Switch logic version
- Survival / Suitability logic versions
- Double-Play logic version
- Entry / Position / Exit decision-logic version

Die Identity muss insbesondere verhindern, dass Ergebnisse aus unterschiedlichen Versionen der kanonischen Handelslogik still als dasselbe Experiment oder als methodisch identische Kandidaten behandelt werden.

Eine Änderung an einer für das Experiment wirksamen Bull/Bear-, State-Switch-, Survival-, Suitability-, Double-Play- oder Entry-/Exit-Entscheidungslogik muss die entsprechende Core-Logic-Bindung und damit die Experiment Identity ändern.

## Exit Gate

```text
EXPERIMENT_IDENTITY_COMPLETE=true
EXPERIMENT_REPRODUCIBILITY=COMPLETE
IMPLICIT_CRITICAL_INPUTS=0
CANONICAL_TRADING_DECISION_CORE_BOUND=true
CORE_LOGIC_VERSION_DRIFT_DETECTABLE=true
```

# 13. Phase 8 – Regime-Aware Evaluation

## Ziel

Strategien werden nicht nur global bewertet.

## Zu analysierende Kontexte

Mindestens:

- trend / range
- high / low volatility
- bull / bear
- liquidity state
- spread regime
- funding regime
- crash state
- risk-on / risk-off
- volatility clustering
- venue microstructure state

## Je Strategie

Speichern:

- return per regime
- Sharpe per regime
- drawdown per regime
- turnover per regime
- fee drag per regime
- slippage per regime
- failure rate per regime
- sample size per regime

## Canonical Core-Logic Attribution

Regime-Aware Evaluation darf nicht bei einer bloßen Gruppierung von PnL nach `bull / bear` stehen bleiben.

Für die kanonische Trading Decision Chain soll – soweit fachlich beobachtbar und ohne Lookahead – versionierte Evidence die Wirkung einzelner Entscheidungsstufen attributierbar machen:

```text
Market Context
→ Bull/Bear Classification
→ State Switch
→ Survival
→ Suitability
→ Double Play
→ Entry / Position / Exit
→ Economic Outcome
```

Dabei müssen insbesondere Fehlklassifikation, Timing-Fehler, Gate-/Filter-Fehler, Execution-/Cost-Effekte und tatsächliche Strategy-Edge voneinander unterscheidbar werden, soweit die verfügbare Evidence dies belastbar unterstützt.

Das Learning System darf dabei keine nachträgliche Kenntnis zukünftiger Marktbewegungen in Runtime-Features oder historische Decisions zurückleaken.

## Architekturproblem

Research-Regime und Runtime-Regime dürfen nicht still als identisch behandelt werden.

Es braucht entweder:

1. einen expliziten Mapping Contract,
2. oder eine bewusst dokumentierte Trennung.

## Exit Gate

```text
REGIME_AWARE_EVALUATION_PRESENT=true
REGIME_MAPPING_EXPLICIT=true
REGIME_LOOKAHEAD_BLOCKED=true
CANONICAL_CORE_LOGIC_ATTRIBUTION_PRESENT=true
BULL_BEAR_DECISION_QUALITY_EVALUABLE=true
```

# 16. Phase 11 – Meta-Learning

## Ziel

Peak_Trade lernt nicht nur den Markt, sondern seinen eigenen Research-Prozess.

## Fragen

- Welche Strategiefamilien überleben OOS?
- Welche Parameterregionen overfitten?
- Welche Suchräume produzieren False Positives?
- Welche Robustness-Tests sagen Shadow-/Testnet-Erfolg voraus?
- Welche Backtest-Metriken besitzen reale Prognosekraft?
- Welche Cost Models unterschätzen Realität?
- Welche Regime verursachen wiederkehrende Failure Modes?
- Welche Parameter sind langfristig instabil?
- Welche Hypothesenarten erzeugen wiederholt schlechte Ergebnisse?
- Welche Research-Pfade liefern den höchsten Informationsgewinn?

## Beispiel

Später könnte Meta-Learning feststellen:

```text
Backtest Sharpe          -> geringe Prognosekraft
OOS stability           -> mittlere Prognosekraft
fee stress stability    -> hohe Prognosekraft
parameter plateau width -> hohe Prognosekraft
regime concentration    -> negative Prognosekraft
```

Das erlaubt Peak_Trade, bessere Research-Prioritäten zu setzen.

Meta-Learning erzeugt jedoch weiterhin keine Live Authority.

## Exit Gate

```text
META_LEARNING_READY=true
META_LEARNING_AUTHORITY=RESEARCH_ONLY
```

# 21. Goodhart / Optimizer Safety

Optimierer dürfen keine bessere Bewertung erreichen, indem sie lediglich:

- Risk erhöhen,
- Leverage erhöhen,
- Turnover erhöhen,
- Tail Risks verstecken,
- illiquide Situationen ausnutzen,
- Fill-Annahmen ausnutzen,
- Kostenmodelle umgehen,
- Regime overfitten,
- Holdout leaken,
- Parametergrenzen ausreizen.

Deshalb müssen Risk-, Cost- und Robustness-Grenzen außerhalb des Optimizer-Objectives liegen und policy-seitig fixiert sein.

# 27. Final Architectural Principle

Der größte Nutzen entsteht nicht dadurch, dass Peak_Trade immer komplexere Optimierer besitzt.

Der größte Nutzen entsteht dadurch, dass das System langfristig beantworten kann:

```text
Was haben wir ausprobiert?
Warum?
Unter welchen Daten und Kosten?
Wie robust war es?
Warum wurde es verworfen?
Wie verhielt es sich in Shadow/Testnet?
Wo wich Realität vom Backtest ab?
Welche Research-Muster funktionieren langfristig?
Wie gut funktionieren Bull/Bear, State Switch, Survival, Suitability und Double Play tatsächlich?
Welche Stufe der kanonischen Trading Decision Chain verursacht Gewinne, Verluste oder vermeidbare Drawdowns?
War ein Fehler strategisch, regimebedingt, timingbedingt, executionbedingt oder kostenbedingt?
Welche Änderungen am Trading Core sind robuste Research-Kandidaten und welche nur Overfit?
Welche eigenen Research-Ergebnisse verdienen überhaupt Vertrauen?
```

Das Ziel ist daher nicht:

```text
AUTONOMOUS TRADER
```

sondern:

```text
AUTONOMOUS RESEARCHER
+
STRICTLY GOVERNED TRADING AUTHORITY
```

Das ist die empfohlene bestmögliche Zielarchitektur für das Peak_Trade Self-Learning System.
